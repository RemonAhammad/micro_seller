# Micro Seller (SellerBook) — Project Context

A Flutter inventory & order management app for micro/small sellers. Local-first with optional Google Drive backup.

## Tech Stack

- **Flutter** (SDK >=3.12.0 <4.0.0; CI builds with the Flutter pinned in `.github/actions/setup-flutter/action.yml`, which `./release.sh` sets to the releasing Mac's version, see Build & Release → Toolchain)
- **State Management:** Riverpod 3 (`flutter_riverpod ^3.3` + `riverpod_annotation` 4.0.2 + `riverpod_generator` 4.0.3, the last two pinned together, see Toolchain). Notes: (1) Riverpod 3 uses plain `Ref` everywhere (no per-provider `XxxRef` typedefs), and `@riverpod class XxxNotifier` generates `xxxProvider` (no `Notifier` infix). `AsyncValue.value` is now nullable; `valueOrNull` is gone. (2) **All CRUD notifiers must be `@Riverpod(keepAlive: true)`** — Riverpod 3 auto-disposes by default, and a `ref.read(xxxProvider.notifier).method()` call from a screen disposes the provider during the await. Post-await `state = ...` then throws `UnmountedRefException`. This applies to product / order / customer / supplier / expense / category / cash_register notifiers.
- **Database:** Isar 3.4 via the community fork — `isar_community` + `isar_community_flutter_libs` + `isar_community_generator` ^3.4.1. The original `isar` package was abandoned in 2023 and shipped 4 KB-aligned native binaries that Play Store rejects on Android 15+. The community fork is API-identical; storage format is byte-compatible (no on-device migration).
- **Navigation:** GoRouter with `StatefulShellRoute` (14-branch sidebar navigation). On iOS, sub-pages slide in and swipe back as native pages, also from the screen edge over the sidebar (see Navigation)
- **Code Generation:** Freezed 3 (`freezed` 3.2.5, pinned, see Build & Release → Toolchain, + `freezed_annotation ^3.1`). Note: freezed 3 requires `abstract class Foo with _$Foo` (the `abstract` keyword is mandatory). JSON serializable + isar_community schema generator.
- **Security:** `local_auth` (biometric) + `crypto` (SHA-256 PIN hashing). `AuthGateService` + `runAuthGate(context, reason: ..., fingerprintEnabled: ..., pinEnabled: ...)` helper protect destructive actions. PIN is stored in SharedPreferences as `sha256(salt + pin)` with a per-install salt. Android: `MainActivity` extends `FlutterFragmentActivity` (required by local_auth's BiometricPrompt) and the manifest declares `USE_BIOMETRIC`. Two-layer gate: (1) **`.env` build-time visibility** — `ENABLE_FINGERPRINT_GATE` / `ENABLE_PIN_GATE` (default `true`) control whether each toggle is shown in Settings → Security at all, and `runAuthGate` ignores any path whose `.env` flag is false; (2) **user setting** — `securityFingerprintEnabled` / `securityPinEnabled` in SharedPreferences (default `true`) control whether the user has each path active. Each toggle in Settings is verified independently — flipping fingerprint requires verifying *current fingerprint only* (never PIN), flipping PIN requires verifying *current PIN only*. Enabling PIN runs `runPinSetup` (fresh setup); disabling clears the stored PIN. `runAuthGate` chooses biometric if (env+user+device-available), else PIN if (env+user+stored), else passthrough. iOS: Face ID needs `NSFaceIDUsageDescription` in Info.plist (see Build & Release → iOS Config), and the Settings row says Face ID or Touch ID there (see Key Business Flows → Face ID label). local_auth 3 reports a cancel (Face ID's Cancel button included), a lockout or missing biometrics as a `LocalAuthException`, not a `PlatformException`; `AuthGateService` catches both (not passed / unavailable), since an uncaught one escaped `runAuthGate` and the screen that asked. It also catches `MissingPluginException` (no local_auth on Linux, the web, widget tests): unavailable, not an error.
- **PDF:** `pdf` + `printing` + `flutter_image_compress`. A Flutter widget is captured to PNG by `widget_capture.dart` (guaranteed Unicode shaping) and `pdf_assembly.dart` builds the A4 `pw.Document` on a background isolate. `widget_capture.dart` is a trimmed copy of the `screenshot` package's capture. `screenshot` is still listed in `pubspec.yaml`, but nothing in `lib/` imports it.
- **File open:** `open_file` package. The post-download bottom sheet uses it to hand a saved invoice PDF to the system PDF viewer. The sheet replaced an earlier SnackBar flow because Material's SnackBar duration was unreliable on MIUI / Xiaomi devices (the timer paused indefinitely). `lib/shared/widgets/pdf_saved_sheet.dart` is a modal sheet with an Open action that runs its own `Timer(Duration(seconds: 15))` for a guaranteed auto-dismiss. iOS has no download folder and no such sheet: the system's save sheet asks where, each time (`savePdfWithSystemSheet`, see Order Form UX).
- **Cloud:** Google Sign-In **7** + Google Drive API (`googleapis` 17) for backup/restore. v7 splits authentication (`GoogleSignIn.instance.authenticate()`, UI) from authorization (`authorizationClient.authorizationForScopes` — no UI — / `authorizeScopes`). `DriveService` only needs authorization for Drive calls, so background/startup paths (`hasDriveAccess()`, `_getDriveApi(interactive: false)`) never show UI. **On Android without google-services.json, v7 requires the *web* OAuth client id as `serverClientId`** — read from `GOOGLE_OAUTH_WEB_CLIENT_ID` in `.env` by `DriveService._ensureInitialized()`; if it's empty, sign-in fails with a configuration error. **On iOS the app's own iOS OAuth client signs in:** Dart passes no `clientId`, so google_sign_in reads `GIDClientID` from `ios/Runner/Info.plist`, which also registers the reversed client id as the URL scheme Google's sign-in page returns through (with no `clientId`, the plugin ignores `serverClientId` there). A missing `GIDClientID`, or a client id without its URL scheme, makes the interactive sign-in raise a native exception Dart can't catch, which closes the app. Drive backup / restore works on iOS; Auto Backup isn't offered there (see Backup/Restore → iOS).
- **Charts:** fl_chart for dashboard sales visualization + reports + customer history
- **Notifications:** flutter_local_notifications for low stock & payment alerts
- **CSV:** `csv` + `file_picker` for import/export
- **Localization:** flutter_localizations + custom delegate (12 languages: en, bn, ar, es, fr, pt, tr, id, th, vi, ur, ms)
- **Persistence:** SharedPreferences for app settings
- **Color themes:** `dynamic_color` **1.8.1, pinned**, for Phone colors (Material You, the Android 12+ system color scheme). 1.9.0 doesn't build on AGP 8 (its Gradle script never applies the Kotlin plugin), and 2.x is built on `package:material_ui`, whose `ColorScheme` isn't Flutter's. The rest is plain Material 3 (`ColorScheme.fromSeed`) plus a `BrandColors` theme extension. See Key Business Flows → Color themes
- **Env config:** `flutter_dotenv` loads `.env` at startup (OAuth client IDs, gitignored; `.env.example` is the tracked template)
- **Onboarding:** showcaseview v5 for first-time guided tour
- **In-App Update:** in_app_update for Play Store auto-update prompts, on Play installs only. The iPhone app and APKs installed from GitHub get a notice of the latest GitHub release instead (`http` + `package_info_plus`'s `installerStore`, see Key Business Flows → Update notice)
- **Fonts:** Roboto on every platform. Android draws its system Roboto (variable, so real w600 / w800). iPhones ship San Francisco, so the app bundles static Roboto (`assets/fonts/roboto/`: Regular, Medium, Bold, Black and `Roboto_LICENSE.txt`, Apache-2.0, from the Flutter SDK's `material_fonts`, about 690 KB) as the pubspec family **`RobotoStatic`**, and the theme names `appFontFamily` (`app_fonts.dart`): `RobotoStatic` on iOS, `Roboto` elsewhere. It isn't named `Roboto` because a bundled family wins over the system's, and Android would lose its real w600 / w800. With the static files w600 draws as Bold and w800 as Black, which is what the layout tests always measured. Scripts Roboto lacks (Bengali, Arabic, Urdu, Thai, the ৳ sign) still fall back to each phone's own fonts
- **Device channel:** the app's own `MethodChannel('micro_seller/device')` (`device_channel.dart`), for what the plugins don't tell: the camera permission's state, opening the app's page in the system's Settings, and the iPhone's biometry type. No plugin: Android answers in `DeviceChannel.kt`, iOS in `AppDelegate.swift` (see Build & Release)
- **Icons:** the **whole app** uses thin Tabler line icons (`tabler_icons_next`, SVG via `flutter_svg`) — no Material `Icons.*` / `Icon(...)` anywhere in `lib/`. Use `ThinIcon(tabler.Plus.new, size:, color:)` (a drop-in for `Icon`, defaults from `IconTheme`; like `Icon`, it draws at its own size centered in a bigger forced box, so no call site needs a `Center`) with `import 'package:tabler_icons_next/tabler_icons_next.dart' as tabler;`. Icons are Tabler **constructor tear-offs** (`tabler.Box.new`), typed `ThinIconBuilder`; they're compile-time constants, so `const ThinIcon(...)` and `const` lists work. Widgets that take an icon (`EmptyState`, `ConfirmDialog`, `AppButton`, `StatCard`, `SidebarItem`, …) take a `ThinIconBuilder`, not `IconData`. Shared named icons live in `AppIcons` ([app_icons.dart](lib/core/constants/app_icons.dart)). Stroke `kIconStroke = 1.25` (`kIconStrokeSelected = 1.75` for the active sidebar tab; Tabler's default is 2.0). The theme's `actionIconTheme` swaps Flutter's own back / drawer / close buttons for Tabler too (back arrow flips in RTL). History: `phosphor_flutter` 2.1.0 doesn't compile on Flutter 3.44 (extends the now-`final` `IconData`); Lucide and Fluent were judged too bold. `flutter_svg` is a direct dependency only so `main()` can set `svg.cache.maximumSize = 300`. The app draws about 140 distinct (icon, stroke) SVGs, and with the default limit of 100, evicted icons were re-parsed on an isolate and appeared a frame late. `warmThinIcons` (in `app_icons.dart`) pre-parses the sidebar icons at both strokes, plus `AppIcons.dashboardSet`, after the first frame.
- **Package versions (upgraded 2026-09-30 to latest for Flutter 3.44):** share_plus 13 (`SharePlus.instance.share(ShareParams(...))` — `Share.share` is deprecated), file_picker 13 (static `FilePicker.pickFile` / `getDirectoryPath` / `saveFile`; read `PlatformFile.readAsBytes()` because SAF content URIs have no path), csv 8 (`csv.encode` / `csv.decode`), fl_chart 1.x (`tooltipBorderRadius`), local_auth 3 (`authenticate(biometricOnly:, persistAcrossBackgrounding:)` — no `AuthenticationOptions`), flutter_local_notifications 22 (named `initialize(settings:)` / `show(id:, title:, body:, notificationDetails:)`), go_router 18, mobile_scanner 7, package_info_plus 10, in_app_update 5, open_file 4, flutter_dotenv 6, flutter_lints 6. After a major plugin upgrade run `flutter clean` — a stale Gradle Kotlin cache made share_plus 13 fail to compile until cleaned.
- **Other:** image_picker, mobile_scanner v7 (QR), url_launcher, intl

## Architecture

Feature-based modular structure with repository pattern:

```text
lib/
├── main.dart                     # Entry point: .env ∥ SharedPreferences, currency init, `TutorialService.primeFrom` + `DisplayScale.primeFrom` + `Settings.primeFrom` (so the first frame is already at the saved Display / Text size, theme mode and color theme). When Phone colors is the saved theme, it awaits `DynamicColorSupport.prime()` (the system palette, 500 ms timeout); then `publishDocumentBrand` gives the PDFs their color. `OrientationPolicy.install()` (phones portrait, tablets rotate), the first frame's status bar (`initialSystemUiStyle`, from `Settings.primedThemeMode` and whether the splash will show), SVG cache size, ProviderScope; notification init (awaited before runApp on iOS only); icon warm-up + Workmanager (Android only) after the first frame (see Performance → Startup)
├── app.dart                      # Root MaterialApp, theme (light/dark/system + color theme), GoRouter, Isar warmup, localization. One `select` reads only themeMode / language / shopName / `colorThemeId` / the custom themes' JSON text (plain values, so the record compares cheaply), and the color theme is resolved once per (id, JSON). A `DynamicColorBuilder` wraps `MaterialApp.router` (Phone colors); `theme` / `darkTheme` are the memoized `AppTheme.build(brightness, colorTheme, dynamicScheme:)`, and each build calls `publishDocumentBrand`, which writes only on a change. `builder` is `AppFrame` (`app_frame.dart`: the status bar style, tap-outside unfocus, the Display size zoom and iOS's keyboard bar, around the Router). Post-first-frame: `purgeExpired()`, plus the auto-backup catch-up 15 s later (a no-op on iOS, `AutoBackupRunner.isSupported`)
├── core/
│   ├── constants/
│   │   ├── app_distribution.dart # `AppDistribution`: the GitHub repo (`RemonAhammad/micro_seller`), `latestReleaseApi`, `releasesPage`, `playInstaller` (`com.android.vending`), `appStoreId` (null while the iPhone app is only sideloaded, so iOS offers no rating)
│   │   ├── app_colors.dart       # Teal's brand constants (`primary` #00897B, `primaryDark`, `primaryLight`, `accent`, `dashboardGradient`): they make up `BrandColors.teal`, and only the theme files and the first-launch splash may use them (`test/theme_usage_test.dart`); widgets read the active theme. Fixed, never themed: status / payment / tag colors and the chart series (`chartRevenue`, `chartProfit`)
│   │   ├── app_icons.dart        # `ThinIconBuilder`, `ThinIcon` (drawn at its own size, centered in whatever box its parent forces — `_CenteredIcon`, as `Icon` centers its glyph; the SVG fills the box it gets, so a text field's 48 dp prefix slot used to draw a 20 dp icon at 48; the whole box still takes hits), stroke constants, `AppIcons` (+ `dashboardSet`; `update` is the update notice's), `warmThinIcons` (SVG cache warm-up)
│   │   ├── app_sizes.dart        # Spacing, radius, icon size tokens
│   │   ├── app_strings.dart      # 100+ string constants (localization-ready)
│   │   └── sidebar_items.dart    # `SidebarItem` (stable key, branchIndex, icon, color), `sidebarItems`, `reconcileSidebarOrder`
│   ├── extensions/
│   │   └── context_extensions.dart  # Theme, snackbar, confirm dialog shortcuts. The undo snackbar's action is the theme's `brand.primaryLight`, mixed toward white until it reads 4.5:1 on the bar's #323232 (Teal's #4DB6AC already does)
│   ├── l10n/
│   │   ├── app_localizations.dart   # Custom LocalizationsDelegate (12 locales)
│   │   ├── translations_en.dart     # English (~700 keys, source of truth) + parameterized helpers

│   ├── router/
│   │   ├── app_router.dart       # GoRouter config (`initialLocation` is `/splash` only until the splash has been shown), 14-branch sidebar navigation shell, SafeArea wrapper. The shell watches only `sidebarPosition`, and the sidebar only the order and hidden set, via `select`. The shell also runs the first-run sidebar tour (see First-Time Showcase Tour). Sub-routes are built by `_subPage`: a `MaterialPage` on iOS, `_fadePage` on Android and the web. Every branch is built by `_branch`, which gives it a `BranchTopRouteObserver`, and the shell body sits in `ShellEdgeBackSwipe` (see Navigation → Sub-pages and iOS swipe back). Exports the sidebar's sizes: `kSidebarRailWidth` (56), `kSidebarExpandedWidth` (200), `kSidebarExpandMinWidth` (600)
│   │   └── shell_back_swipe.dart # iOS back swipe from the screen edge over the sidebar: `BranchTopRouteObserver` (a branch navigator's top route) and `ShellEdgeBackSwipe` (a 20 dp strip, or the edge inset if wider, driving the page's public back-gesture API)
│   ├── theme/
│   │   ├── app_theme.dart        # `AppTheme.build(brightness, colorTheme, {dynamicScheme})`: `ColorScheme.fromSeed` in the theme's style, then the theme's exact primary / onPrimary pair and its accent as secondary; Phone colors use the system scheme as is. Memoized (the 32 most recent; the editor builds one per color it previews) by brightness + platform + the colors that mode uses, not id or name, so a language or shop-name rebuild gets the identical `ThemeData` (the platform decides the font and what ThemeData derives from it). - **Isar does not return equal index keys in id order** (it uses stored-id byte order). Rows loaded through an index that feed money sums are re-sorted by id (`..sort((a, b) => a.id.compareTo(b.id))`, `_byId` in reports_provider), so floating-point sums add in the same order as before and stay bit-identical. `test/worker_parity_test.dart` checks this. - **A string part used for ordering must be `IndexType.value`.** Strings default to a hash index, which has no order.
```

## Key Business Flows

### Order Creation (transactional)

1. Customer is required (validated in form)
2. Save order to DB — each OrderItem stores `costPrice` from the product at time of order (frozen for accurate profit)
3. OrderItem stores `variantCombinationKey` + `variantDisplayLabel` if a variant was selected (legacy `variantName`/`variantValue` are only read as a fallback for pre-migration orders)
4. Tax amount is calculated from the per-order tax rate field and stored on the order
5. If status == confirmed: deduct stock per item (**both base `stockQty` and variant `stockQty`**) + create StockMovement records
6. If customerId > 0: update customer totalOrders, totalSpent, outstandingBalance
7. `createOrder` returns `Future<int>` (the new order's Isar id) so the form can hand the saved order to the post-creation invoice sheet without a follow-up query

### Order Editing

1. Load existing order by ID into the form
2. Pre-populate all fields (customer, items, pricing, tax rate, status, payment method, delivery, recurring)
3. On submit, update order preserving original id, orderNumber, createdAt

### Order Status Change (rollbackable)

- **Forward** (pending → confirmed/shipped/completed): deducts stock (base + variant), creates sale StockMovements
- **Rollback** (confirmed/shipped/completed → pending/cancelled): **restores stock** (base + variant), creates adjustment StockMovements with "Rollback" reason
- **Cancel:** Available from any non-cancelled state via popup menu on order detail screen
- Logic: pending/cancelled = stock not deducted; confirmed/shipped/completed = stock deducted
- Long-press any order card in the list to change status via popup menu
- Every stock move (sale, rollback, cancel, delete, return approve) goes through `OrderNotifier._moveStock(items, sign:, type:, reason:)` inside the caller's `writeTxn`. It runs one `getAll` for the products, applies items **in order** to an in-memory map keyed by product id (so two variants of one product compose exactly as sequential get → put did), then one `putAll` for products and one for StockMovements. Items whose product is gone are skipped, movement included. It replaced a get + put + put per item, each a round trip to Isar's thread. `test/batched_writes_test.dart` pins the numbers

### Order Deletion (safe)

- **Restores stock** (base + variant) if order was confirmed/shipped/completed (creates adjustment StockMovements)
- **Reverses customer stats** (totalOrders, totalSpent, outstandingBalance)
- Then deletes the order

### Return Orders

1. "Create Return" action from order detail screen (hidden for return orders themselves)
2. Create return screen shows items with variant info via `displayName`, qty selector, reason chips
3. **Refund amount capped at `amountPaid`** on original order (validation + auto-fill cap)
4. Refund of 0 allowed (e.g. exchange)
5. **Valued at what the customer paid:** `createReturnOrder` stores `returnValueFor(original, items)` as the return's subtotal / discountAmount / taxAmount / totalAmount: list price, minus the items' pro-rata share of the order discount, plus their share of the tax (delivery isn't refunded). Not rounded, so piecewise returns add up to exactly the order. The refund pre-fill uses the same function; submitting it unedited refunds the exact value, and the check allows half a paisa over `amountPaid` (the field shows the currency's decimals, `NumberInput.moneyDecimals`; `processRefund` caps at `amountPaid`). At list price, a full return of a discounted order credited the customer the discount against their *other* dues. Returns created before this keep their list-price value (no migration — balances were settled against it).
6. Creates a new order with `RET-XXX` numbering, `isReturn: true`, linked via `originalOrderId`
7. Return detail screen shows only the 3-step return flow (Requested → Received → Refunded), **not** the regular order status stepper
8. On approve: **restores stock** (base + variant) for all items via restock StockMovements
9. **Updates customer stats** (decrements totalSpent)

### Recurring Orders

1. Toggle in order form sets `isRecurring`, `recurringIntervalDays`, `nextRecurringDate`
2. `processRecurringOrders()` checks for due recurring orders and auto-creates new pending copies, all in **one** `writeTxn`. The order count is read once and advanced locally (each copy adds exactly one order, so the `ORD-` numbers match a fresh count per copy). Customers are read with one `getAll`, so a customer with several due orders accumulates on one map entry, and each copy bills them as `createOrder` would. Orders and customers are written with one `putAll` each

### Delivery Tracking

1. Delivery address and estimated delivery date set in order form
2. Order detail shows delivery tracking card with "Mark as Delivered" button
3. Marking delivered sets `actualDeliveryDate` and status to completed

### Profit Calculation

One formula, `buildSalesReport`, feeds both Reports → Gross profit and the Dashboard's profit card and 7-day chart (`profitSeries`), so the two screens can't disagree. The Dashboard used to sum `(unitPrice − costPrice) × qty`, which ignored the order discount (a Play Store review) and took whole cash refunds off profit.

- **Gross profit** = goods at list price − order discounts − returns − COGS. The discount is order-level (`discountAmount`); `Order.discountFactor` spreads it pro rata where per-item revenue is needed (top products, categories)
- **Tax** is never sales or profit — the P&L shows it as "Tax collected"
- **Delivery** (`deliveryIncome`, normally `deliveryFee`) is added below gross profit, so it lands in net profit against courier costs logged as Logistics expenses
- COGS uses `costPrice` stored on OrderItem (frozen at order time); falls back to the product's current cost when 0
- Returns reverse their goods value (`netGoods`) and their COGS on the day the goods came back
- Dashboard shows: filtered profit, weekly profit chart, revenue vs expenses line chart. Its revenue card is unchanged: billed totals minus refunds

### Payment Recording (transactional)

1. Update order.amountPaid, determine paymentStatus (paid/partial)
2. Update customer.outstandingBalance -= payment
3. Log a `Payment` row in the same `writeTxn`. Every `amountPaid` change logs one: `createOrder` (initial payment), `recordPayment`, `collectFromCustomer`, `processRefund` (negative, on the original order), cancel (negative — cancel is an auto-refund). `deleteOrder` deletes the order's rows.

### Due Book (customer credit ledger)

Sellers sell on credit ("baki"); the Due Book is where they get paid back. Own sidebar tab **Due Book** (`/dues`, branch 13, key `dues`), also reached from the Customers appbar and the Dashboard unpaid card.

- **Dues are computed from orders, never from `Customer.outstandingBalance`.** That counter drifts (`updateOrder` doesn't adjust it; recurring copies didn't bill the customer until the Due Book fixed `processRecurringOrders`). The customer's total is `computeNetDue` — every order's effective due *including credits* (an exchange return worth more than an order's remaining due), floored at 0, ignoring orders within `kDueEpsilon` of settled (sub-paisa leftovers on several orders used to add up to a "due" on no order, and `orderDues.first` crashed the Due Book) — so it matches the counter and the statement; collections are capped at it. `computeOrderDues` takes all of a customer's orders *including returns*: excluded are cancelled orders and return orders; each order's effective due is `balanceDue − value of its refunded returns`, because `processRefund` lowers the original's `amountPaid` by the refund but not its `totalAmount`.
- **Loading:** `duesProvider` runs `loadDuesSync` on a worker (`runDbJob`), reloading via `reloadOn` when orders or customers change. It does one id-ordered `filter()` scan of orders with a customer, groups them in Dart, `getAll`s the debtors, and finds each one's last positive payment from two property reads (`customerId`, `paidAt`) instead of a query per debtor. The Dues report reuses the same job, so the two can't disagree.
- **Collect** (`OrderNotifier.collectFromCustomer`): one amount applied oldest-first across the customer's due orders, capped at the total due (no advance credit). The orders are loaded through the customerId index and re-sorted by id, so allocation matches the Due Book. One `Payment` per touched order sharing a `groupId`; the order updates and payment rows are written with one `putAll` each. Cash collections can add to the open cash register in the same transaction. The sheet's allocation preview mirrors the notifier's loop.
- **Remind**: localized WhatsApp text via `https://wa.me/<digits>?text=`. A Bangladeshi local mobile (`01…`, 11 digits) with ৳ gets the `88` prefix; other numbers pass through as typed. No phone / launch failure → share sheet, which on an iPad points at the Remind button that was tapped (`shareOrigin`).
- **Statement**: `StatementService` PDF (running balance). Orders before payment history existed have no `Payment` rows, so each order's unlogged `amountPaid` is shown as a payment on the order date — the closing balance always matches the orders.
- **Recalculate balances** (Due Book overflow menu, and once automatically via `migrateOutstandingBalancesV1`) resets every counter to the computed dues. The menu action runs `recalculateOutstandingBalances(isar)` (load, compute and write in one transaction on a worker) behind `runWithProgress`; on the UI isolate it froze the spinner with thousands of orders. Every restore also recalculates, inside its own write transaction.

### Product Photos

- **Saved** by the product form: picked with image_picker (`imagePickerProvider`) and compressed (`flutter_image_compress`) to `<documents>/product_images/<uuid>.jpg`. A pick or save that fails says so: a snackbar, or for a refused camera the dialog (see Camera access).
- **Stored relative:** `Product.imagePath` holds `product_images/<uuid>.jpg`, and every view resolves it with `resolveProductImagePath` (`product_image_store.dart`) against `ProductImageStore.documentsDirectory`, which the isar provider sets before it opens the database (until then a relative path resolves to no photo). Why: iOS can move the app's data container, and with it the documents directory's absolute path, when the app is updated (a sideloaded build is reinstalled at every 7-day refresh), so an absolute path saved before then pointed nowhere although the photo had moved along. Android's documents directory doesn't move.
- **Older absolute paths:** one inside a `product_images` folder resolves to the same file in today's documents directory; any other absolute path is used as stored. `migrateProductImagePathsV1` rewrites them as relative once, while the database opens (SharedPreferences flag `productImagePathsV1Migrated`; idempotent; `updatedAt` untouched). Paths that arrive later (an older backup restored, a recycle-bin restore) are resolved when read.
- **Missing file, no error:** backups carry the path, not the photo, so a product restored on another phone points at a file that isn't there. The product card, the detail header, the form, the catalog avatars and the catalog pages draw their placeholder instead. `test/product_image_store_test.dart` covers the resolver, the stored form, the card and the migration (on a real Isar database).

### Hierarchical Variant System

Products support **multi-attribute variant combinations**:

1. **VariantAttributes** define dimensions: e.g. Size→[S,M,L], Color→[Red,Blue]
2. **VariantCombinations** are the cartesian product: "Size: S / Color: Red", "Size: S / Color: Blue", etc.
3. Each combination has its own `stockQty`, `priceAdjustment`, `sku`, and `isActive` flag
4. Combinations are identified by a canonical `combinationKey` (sorted alphabetically: "Color:Red/Size:L")
5. **Product form** has a two-step editor: define attributes+options, then auto-generated combination table with bulk actions
6. **Limits:** max 3 attributes, max 15 options each
7. **Migration:** Old flat `ProductVariant` data is auto-migrated to single-attribute combinations on first launch
8. **OrderItem** stores `variantCombinationKey` + `variantDisplayLabel` (denormalized for display)
9. All stock operations (order create/status/delete, return, manual adjustment) use `combinationKey` for per-combination stock tracking

### Backup/Restore (Google Drive, safe)

- Exports **all 10 backed-up collections** as timestamped JSON to Drive appDataFolder. The bytes come from `LocalBackupService.encodeAllBytes`: one read txn, encoded straight to UTF-8 on a worker. The upload is resumable in 8 MB chunks, so big backups are sent and retried piecewise and nothing base64-encodes the whole file on the UI isolate
- Keeps max 5 backups, cleans up old ones (cleanup failure doesn't break upload)
- **Safe restore** (`restoreFromBytes`): snapshot the current DB + settings (`encodeAllBytes`), then `restoreBytes(requireMetadata: true)`, which parses, validates and replaces the DB on a worker in one write transaction. Then apply settings. If anything after validation fails, the snapshot is restored and the error is `rolledBack`; if the rollback fails too, it is `restoreFailed`. A file that isn't a backup is `invalidBackup` with nothing touched. The outcome is thrown outside the rollback's `try` (a successful rollback used to be caught by its own catch and reported as `restoreFailed`). `test/backup_worker_test.dart` covers `rolledBack` (settings failing after the restore; a malformed row) and `invalidBackup`
- **Settings round-trip:** backup payload includes a `settings` field built from `Settings.exportSettings()` (theme mode, color theme and saved custom themes, currency, sidebar order/position/hidden items, shop name and phone, autoBackup, etc.). The auto-backup worker builds the same map with `Settings.exportFromPrefs(prefs)` (`color_theme_settings_test.dart` checks they're equal). Restore re-applies via `Settings.importSettings(map)`. v2 backups (collections only) still restore correctly — `settings` is optional on decode, so the color-theme keys needed no backup version bump.
- **Auto Backup (two-tier):** `Settings.autoBackup` toggle (Settings → Drive section). Enabling it both (a) lets `AutoBackupRunner.runIfDue()` fire 15 s after the first frame (a timer started from `SellerBookApp.initState()`, kept off the startup path) for a fast catch-up (12 h soft de-dupe via `lastBackupTime`), and (b) registers a daily `Workmanager().registerOneOffTask` (uniqueName `auto-backup-daily`, `initialDelay = duration to next 00:05 local time`, `NetworkType.connected` + `requiresBatteryNotLow`) that runs in a background isolate even when the app is closed. The worker re-arms itself for the next 00:05 in its `finally` block, forming a self-rescheduling chain — chosen over `registerPeriodicTask` because the periodic API only promises an interval, not a clock time. Neither path ever triggers interactive sign-in (foreground via `getCurrentUser()` early-return; worker via `backupToDrive(interactive: false)`). When the worker hits `notSignedIn` / `signInFailed` / `developerError` it persists `autoBackupError` in SharedPreferences, fires a "Auto backup paused" notification *once* (subsequent revoke runs skip it), and stops the chain. The Settings → Drive section watches that flag (refreshed on `initState` and `AppLifecycleState.resumed`) and shows an amber banner with a "Sign in to fix" button that re-runs `DriveService.signIn()`, clears the flag, and re-arms the chain via `scheduleAutoBackup()`. Toggling Auto Backup off cancels the worker and clears the banner. WorkManager is Android-only; the helpers `Platform.isAndroid` early-return elsewhere, and iOS has no Auto Backup at all (see iOS below). Native setup: workmanager **0.10.x** (0.5.2 no longer compiles on current Flutter — it used the removed v1 embedding `Registrar` / `ShimPluginRegistry`) auto-registers via the v2 plugin embedding — no MainActivity / Application class changes required. `initialize()` takes no `isInDebugMode` in 0.10.
- **iOS:** Sign in, Backup to Drive and Restore from Drive work as on Android, through the app's iOS OAuth client (`GIDClientID` and its reversed-id URL scheme in Info.plist, see Tech Stack → Cloud). There is no Auto Backup (`AutoBackupRunner.isSupported` is false): no WorkManager worker, no start-up catch-up, and Settings hides the switch and the paused banner, also when a backup restored from an Android phone turned `autoBackup` on. Sideloading tools may re-sign the app under another bundle ID, which the iOS client isn't registered for: Google sign-in then fails with an error (not a crash), and Settings adds `googleSignInSideloadHint` (use Local Backup). `test/drive_ios_test.dart`
- Validates backup structure (`version`, `timestamp`) before touching local data
- **Typed errors:** `DriveBackupException` with `DriveErrorCode` (`notSignedIn`, `signInFailed`, `developerError` for ApiException 10, `network`, `invalidBackup`, `uploadFailed`, `downloadFailed`, `restoreFailed`, `rolledBack`). UI switches on the code instead of substring-matching messages. Settings shows each code as a localized `driveError…` string (`unknown` as `errorOccurred`); the exception's `message` is English detail for the log, never shown.
- **Logging:** every failure logs the error + stack via `dart:developer` and `debugPrintStack` in debug builds.
- **OAuth scope:** `drive.appdata` — backups live in a hidden app-data folder; not visible at drive.google.com.
- **OAuth client IDs** are stored in `.env` (gitignored). Since google_sign_in 7, `GOOGLE_OAUTH_WEB_CLIENT_ID` is **required at runtime** on Android (passed as `serverClientId`); the Android client ids still just need to exist in the Cloud project with the right package + SHA-1. The iOS client id is not read from `.env` (`GOOGLE_OAUTH_IOS_CLIENT_ID` in `.env.example` is unused): it is `GIDClientID` in `ios/Runner/Info.plist`, committed, since client ids aren't secrets, and the client is registered for the bundle ID `com.blackshadowsoftware.microseller`.

### Undo & Recycle Bin

Before this, `grep -r 'undo|trash|deletedAt' lib/` returned one string constant in a warning dialog — deletes were safe for data integrity but permanent for the user.

- **One generic `TrashEntry` collection** rather than `deletedAt` flags on each model, viable because all 13 models implement `toJson`/`fromJson`. No query in the app needs to learn to filter deleted rows.
- **Deletes are not pure**, so the payload alone is not enough to restore. Each entry carries a `sidecar` of what else the delete touched:

  | Delete | Side effect | Sidecar |
  | --- | --- | --- |
  | Customer | Zeroes `customerId` on their orders | `unlinkedOrderIds` — re-linked on restore, skipping orders since deleted |
  | Product (soft) | Sets `isActive = false` | `softDeleted: true` — restore flips the flag on the *current* row, preserving edits made since |
  | Product (hard) | Also wipes the product's StockMovements | `softDeleted: false` + the movement JSONs |
  | Expense, Category | None | `{}` |

- `capture()` runs **inside the delete's own `writeTxn`**, so the trash entry and the delete can never diverge. `restore()` likewise runs the payload put + side-effect reversal in a single transaction.
- **Two UX layers:** a 10-second `showUndoSnackBar` (in `context_extensions.dart`) on each delete, and Settings → Recycle Bin for the full 30-day window. The snackbar is only a convenience — MIUI's known SnackBar-timer stall (the quirk that made `pdf_saved_sheet.dart` own its `Timer`) is harmless here, since the record is recoverable from the bin either way.
- **Phase A covers expense, category, customer, product.** Order, purchase and supplier still delete permanently — their reversal touches stock, variant stock, movements and party stats. `TrashService.restore` throws `UnsupportedError` for those kinds and the bin renders them with restore disabled, so no path offers an action that would fail.
- **Both bulk-clear paths clear the trash too.** Restore and Settings → Clear All Data share `clearAllCollectionsInTxnSync` (`local_backup_service.dart`), which clears each collection *explicitly* (not `isar.clear()`), trash included. A surviving `trashEntries` row would reference ids from the replaced dataset, and restoring it would corrupt live data. A new collection must be added there, which covers both paths. Trash is deliberately **not** part of the backup payload.
- `purgeExpired()` runs post-first-frame from `app.dart`, wrapped in a try/catch — a failure must never block startup.

### Update notice (iPhone and GitHub APKs)

Installs that no store updates — the sideloaded iPhone app and Android APKs from GitHub Releases — hear of a newer release from the app itself.

- **Channel** (`readUpdateChannel`, `updateChannelProvider`): iOS → github (iOS reports `com.apple` as the installer even when sideloaded); Android with installer `com.android.vending` → play, anything else (null, the package installer, a browser) → github; desktop and web → none. A Play-signed APK copied on by hand reports a non-Play installer and counts as github, an accepted edge.
- **Check** (`ReleaseUpdateService.check()`): GitHub's `releases/latest` API (`AppDistribution.latestReleaseApi`), at most once in 24 h (also when the clock moved back), 10 s timeout; calls made meanwhile share one request, and every attempt is stamped, so a failing one waits too. A release counts when it is stable (not a draft or pre-release, a tag that parses without a pre-release part) and carries this platform's file (`.ipa` on iOS, `.apk` on Android); its page must be in this repository, else the releases page is offered. A 404 or a release that doesn't count forgets the cached one; a rate limit (403, 429), a 5xx, a timeout, no connection or bad JSON keep it, silently, so the notice still shows offline. It shows when the cached release is newer than the installed version (`AppVersion`: numeric, a `v` prefix, a pre-release lower) and not snoozed. An iOS release candidate is built with the plain version (release.yml drops `-rc` for Apple), so it isn't offered that version's final release, only later ones; an Android rc keeps its `-rc` and is.
- **Per-device prefs** `update_notice_checked_at`, `update_notice_latest_tag`, `update_notice_latest_url`, `update_notice_snoozed_tag`, never in a backup (`exportSettings` exports only the keys it names).

### Number input (typing amounts)

A phone's number pad types its own region's digits and decimal mark: an iPhone set to France types `12,50`, one set to an Arabic region `١٢٫٥٠`, a Bengali keyboard on Android its own digits. `double.tryParse` reads none of them, so such an amount used to save as 0, or its button did nothing. Every number field, on both platforms, goes through `number_input.dart`:

- **Formatters:** amounts `DecimalInputFormatter.money()` (`signed: true` for a variant's price adjustment), percentages `.percent()` (2 decimals), whole numbers `IntegerInputFormatter()`, phones `PhoneInputFormatter()` (digits, a leading `+`, spaces, `-`, parentheses). They keep the text canonical: ASCII digits, '.' as the point, '-' first only in a signed field.
- **Reading:** `NumberInput.parseDecimal` / `parseInteger` (any script's digits, ',' or '٫' as the point; null for '', '.', '-'), the validators included. There is no `CurrencyFormatter.parse`.
- **Typing:** any script's digit becomes 0-9 (one UTF-16 unit each, so the caret never moves). '.', '٫' and '．' are the point. A ',' is the point on iOS (the decimal pad has one separator key, the region's mark) and, elsewhere, only where the device region writes decimals with one (`NumberInput.deviceDecimalSeparator`, `PlatformDispatcher.locale` through intl: France, Brazil, Indonesia, Vietnam); in Bangladesh, India or the US it groups thousands and is left out, as before. A point typed first gives `0.`. A key that would leave the form (a third decimal, a second point) is refused with the caret kept; deleting never is. Text the app filled with more decimals than the field types stays editable as long as an edit adds none.
- **Pasting** (`NumberInput.normalize`, also the paste button's path through the formatters): invisible direction marks (text copied from Arabic or Urdu carries them) are dropped; '٬', spaces and apostrophes group; a currency symbol or code, '%', '٪' and parentheses at the ends are trimmed. With both '.' and ',', the last is the point; a mark used twice groups; a single mark before exactly 3 digits groups, in a money or whole-number field, when it isn't the region's decimal mark (Bangladesh: 1,250 → 1250 but 1.459 → 1.459; France the reverse). Where the region isn't known a ',' groups (the app's own `1,250`) and a '.' groups unless the field takes 3 decimals (KWD `25.000`). Groups must be thousands or South Asian lakhs / crores (`1,25,000`), else the paste is refused rather than read as another number; so is a negative value in an unsigned field (-50 never becomes 50). Extra decimals round half up. Whatever `CurrencyFormatter.format` writes, KWD's 3 decimals included, pastes back as the same amount in a '.' region or an unknown one; in a ',' region its `1,250` reads by the region, as 1.25.
- **Money decimals:** `NumberInput.moneyDecimals`, read when the text changes: 2, or 3 for the Kuwaiti Dinar (see Currency System).
- **Phone searches** compare with `NumberInput.phoneMatches` (customer list, Due Book, the order form's customer picker, the supplier pickers), and `CustomerRepository.search` converts its query too: phones are saved in 0-9.
- **Guard:** `test/number_input_usage_test.dart` fails on `digitsOnly` anywhere in `lib/`, a digit-pattern field filter (`^\d`, `FilteringTextInputFormatter` on digits) in `lib/features`, or a raw `double` / `int` / `num` parse outside its allow-list (route ids, the CSV import, release tags, hex colors, the parsers themselves).

### Display size & Text size

Settings → Display: two per-device knobs, for phones where the app's coded dp come out too small or too large.

- **Display size** zooms the whole UI (layout, text, icons, spacing), 80–130% in 5% steps, default 100%. **Text size** follows the phone's font size (default) or is a custom 80–130% in the same steps; switching "Follow phone" off starts at 100%. Each is a sheet (`display_size_sheets.dart`) with a slider, a live preview and **Reset** (100% / follow the phone).
- **Applied when the finger lifts** (or on a tap, an arrow key, a screen reader's adjust), not while dragging: applying mid-drag would rescale the sheet, and the slider with it, under the finger. For the same reason the preview box keeps its height while the slider is held. A gesture the slider loses (the sheet's drag or scroll takes it) or that the system cancels applies nothing.
- **Storage:** `displayScaleProvider`, SharedPreferences `displayScalePercent` / `textScalePercent`. Not in the app's backups (`exportSettings()` leaves them out, `importSettings` ignores them): the right size depends on this screen and the phone's own font setting, so a phone backup restored on a tablet must not resize it (same precedent as the rating prompt's state). Android Auto Backup (the manifest doesn't turn `allowBackup` off) can still bring the prefs to a new phone; the width cap below keeps that safe. Stored values are snapped and clamped (`snapPercent`); a corrupt one falls back to the default.
- **First frame:** `DisplayScale.primeFrom(prefs)` runs in `main()` before `runApp`, so the app never draws a frame at 100% and then jumps.
- **One zoom at the root:** `AppZoom` sits in the app frame (`AppFrame`, `MaterialApp.router`'s `builder`), around the Router, so every route, dialog, sheet, menu, tooltip and snackbar is zoomed alike and no screen has to know. The child is laid out at the window size ÷ scale and painted × scale (`RenderZoomBox`; hit tests, semantics and `localToGlobal` go through the same transform), so it always fills the window. `zoomMediaQuery` rewrites the MediaQuery to match:
  - size, padding, viewPadding, viewInsets, systemGestureInsets, display features and corner radii ÷ scale, so SafeArea, the keyboard inset and hinge avoidance still add up to the window
  - devicePixelRatio × scale, so images still decode at the screen's physical resolution
  - `gestureSettings` untouched (drag slop is compared in window units); `supportsShowingSystemContextMenu` kept
  - textScaler replaced only by a custom Text size; at 100% with no custom Text size the app gets the window's MediaQuery as is
- **Same tree at every size, 100% included:** a size change relays out the app but never remounts the Router, the shell or a branch navigator, so no screen loses state or reloads. At 100% `RenderZoomBox` paints the child directly, with no transform layer. PDF and catalog captures build their own tree and are never zoomed.
- **320 dp minimum layout width** (`kMinZoomedLayoutWidth`, the narrowest phone the layouts are built for): `maxDisplayPercentFor(windowWidth)` caps zooming in so the layout stays at least 320 dp wide — 125% on a ~411 dp phone, 110% on a 360 dp one, never below 100%. Zooming out is never limited. The slider ends at the cap, and Settings shows the size in effect (`AppZoomScope.displayPercent`), which a narrow window can hold below the saved one.
- **`AppZoomScope`** gives the scale, the capped percent and the window's own MediaQuery (`outer`) to widgets that need window values (the sheet's cap, the phone's font size, `ZoomNeutral`). It doesn't notify on padding / inset-only changes, because the keyboard moves them on every animation frame.
- **`ZoomNeutral`** cancels the zoom for a subtree (window dp; the Text size still applies), for Flutter widgets that mix window and local coordinates. `ReorderableListView`'s drag proxy and drop slots only agree unscaled (zoomed, the dragged row was drawn away from the finger), so Sidebar Order runs its list in `ZoomNeutral` with its own unclipped `Overlay.wrap` for the proxy, and draws each row back at the zoom with a `ZoomBox`.
- **Tour:** skipped (and marked completed) when zoomed — see First-Time Showcase Tour.
- **iOS edit menu:** Flutter positions text-selection menus by adding a field's on-screen position (zoomed) to offsets inside the field (not zoomed). iOS keeps its system edit menu (Cut / Copy / Paste act on the right selection, but the menu points `(1/s − 1) × d` beside it). Turning `supportsShowingSystemContextMenu` off while zoomed was worse: Flutter's Cupertino toolbar points at the same wrong spot, drifts at the screen edges, and its Paste brings back iOS's "Allow Paste" prompt. A fix would need a `contextMenuBuilder` on every field (Flutter has no app-wide default). The details are in `app_zoom.dart`'s library comment; `app_zoom_platform_test.dart` fails if a Flutter upgrade fixes the target, so the comment gets updated then.
- **Known limitations** (none at 100%): Flutter-drawn selection toolbars (Android, desktop) can sit slightly off, near the screen edges, when zoomed; a right-click menu opens a little away from the pointer; a toolbar hidden by a scroll may not come back for a selection near the keyboard (a tap shows it). Native surfaces — the share sheet, file / image pickers, notifications, the print dialog — are drawn by the OS and follow the phone's own sizes.
- **Layout rule:** every screen must lay out cleanly — nothing overflows or is cut off, no label is split mid-word — at 320 / 360 / 411 dp × text 1.0 / 1.3 / 1.5 (`kLayoutWidths` × `kLayoutTextScales` in `test/support/layout_harness.dart`), and look unchanged at 100% text on a normal phone. The tools: `ButtonPair`, one-line amounts in `FittedBox(scaleDown)`, slot heights computed from the text scaler (`statCardHeight`, `dashboardHeaderHeight`, `reportsHeaderHeight`), rows that measure their text and stack when it won't fit side by side, and Settings rows that move their control under the title (`_EndControl`, and `_SwitchRow` for switches). Screens also lay out on tablets and in Split View (`forEachTabletLayout`: `kTabletScreens` portrait and landscape, `kSplitViewWidths`, text 1.0 / 1.5), beside the sidebar the app gives that window (`railWidthFor`). A helper that measures text must measure it as `Text` draws it: ambient style, `MediaQuery.textScalerOf`, and **Bold text** (`MediaQuery.boldTextOf` → `FontWeight.bold`), as `measureTextWidth` in `stat_card.dart` does; otherwise it under-measures when the phone's Bold text is on.

### Color themes

Settings → Theme → **Color theme** (`/settings/color-theme`) picks the app's main color: Phone colors, one of 12 presets, or one of the seller's own themes, applied on tap. The default, **Teal**, looks exactly as before themes, except for one readability fix: dark-mode buttons and the FAB put black text on #4DB6AC (white there was 2.44:1).

- **A theme changes only the primary color:** the main color, the White or Black text on it (`onPrimary`), and what Material 3 derives from the main color (containers and tints, from `ColorScheme.fromSeed` in the theme's style). That covers buttons and the FAB, the Dashboard / Reports headers and their gradient, the Due Book summary card, selected chips and tabs, switches, sliders, progress indicators, focused fields, text selection, Settings' row icons, report tints, the date-range picker, the undo snackbar's action and the PDFs. Widgets read `context.brand` (`BrandColors`) or the color scheme, and text on the main color is `onPrimary`, never `Colors.white`. `test/theme_usage_test.dart` fails on an `AppColors` brand constant outside the theme files and the first-launch splash, and on white set on a primary background.
- **It never changes:** the sidebar icons (every tab keeps its own color, selected tint included; `sidebar_items.dart`, the rail's tiles and Sidebar Order don't read the theme), status / payment / tag colors, the chart series (`chartRevenue`, `chartProfit`), the aging bar, the scaffold, app bar, `Card` and text-field backgrounds (surfaces read from the color scheme, like `cs.surface`, take a faint tint of the main color), the launcher icon, the native splash, the first-launch splash animation and the PDF watermark.
- **Presets** (`kPresetColorThemes`): Teal, Blue, Indigo, Purple, Pink, Red, Orange, Amber, Green, Brown, Slate and Mono ("Black & White"). Each is a curated light pair plus a dark pair (`darkPrimary` / `darkOnPrimary`, all with black text). Every pair reads at least 4.5:1 and every main color is at least 3:1 against its mode's background, except Teal's light pair, which keeps white on #00897B (4.32:1). Orange and Amber use black text, because white on an orange that still looks orange is below 4.5:1; light Amber is a deep #B07D00, because #FFC107 is 1.6:1 on the light background. Mono is Vivid, because Soft tints a hueless seed pink. **Customize** (beside the preview, or a long press on a preset) copies a preset into the editor with its name and text color.
- **Phone colors** (Material You): Android 12+'s system scheme from `DynamicColorBuilder`, with the system's own `onPrimary`. Offered only where `dynamicColorAvailableProvider` is true. It stays listed while active, so a backup restored on an older phone shows why the app looks Teal (with no system scheme it draws Teal's colors).
- **My themes:** up to 12 saved themes (`kMaxCustomColorThemes`; ids `custom-<microseconds>`, names up to 30 characters). A tap applies one; ⋮ edits or deletes it, and deleting the active one selects Teal. Create theme is disabled at 12 and starts from the active theme's main color.
- **Editor** (`ColorThemeEditor`): a draft until Save, which saves and selects it. Name, main color, Text color, style (Vivid / Soft / Muted: how colorful the derived tints are), an optional accent, and a live preview in light or dark mode. A main color below 3:1 against the light or dark background gets a hint for that mode; colors are never changed silently. The accent's text color is picked by contrast, so the accent can't get an unreadable pair. It starts as the accent Material derives, so switching it on changes nothing until a color is picked.
- **Text color on the main color: White or Black, nothing else.** The higher-contrast one is marked **Recommended** and is the default. Each option shows how it reads on the main color: "Easy to read" (≥ 4.5:1), "OK for large text" (≥ 3:1) or "Hard to read" (below 3:1, allowed but flagged). Changing the main color moves the choice to the new Recommended one unless the seller picked one by hand; a saved theme whose choice isn't the Recommended one counts as picked. A custom theme's pair is used exactly, in light and dark mode alike, so the preview is what the seller gets.
- **Saved and backed up:** `Settings` keys `colorThemeId` and `customColorThemes`. Unlike Display / Text size, which are per-device, both go into `exportSettings()` and so into every backup. `importSettings` applies the custom themes first (valid ones only, at most 12), then the id: an id the backup doesn't carry selects Teal, and a backup from before themes changes neither.
- **First frame:** `Settings.primeFrom(prefs)` in `main()` reads the theme mode and the color theme before `runApp`, so a cold start is in them from the first frame, with no Teal frame first. For Phone colors, `main()` also awaits `DynamicColorSupport.prime()` (at most 500 ms), which converts the system palette exactly as `DynamicColorBuilder` will, so the builder's later answer gets the identical cached theme.
- **Documents follow the theme:** PDF pages are captured without the app's `Theme` (`captureScope` gives them only a fallback one, for the font), so `publishDocumentBrand` (called from `main()` and every app build) puts the theme's light-mode main color and its text color into `DocumentBrand`. The invoice header and the statement, report and catalog accents and header text follow it (Phone colors: the system's main color, text by contrast). The "Powered by Micro Seller" watermark stays teal (`kPdfWatermarkColor`). Both receipt caches (order detail, post-creation sheet) are keyed on the document colors.

### Closing the keyboard

Flutter leaves the keyboard open on a touch outside the field, and iOS's number, decimal and phone pads have no key that closes them or moves on.

- **Tap outside** (`TapOutsideUnfocus`, both platforms, in the app frame above every route, dialog and sheet): it overrides the two intents a focused `EditableText` invokes for a pointer outside it (`EditableTextTapOutsideIntent` down, `EditableTextTapUpOutsideIntent` up; looked up from the field's context, so this ancestor wins). A touch unfocuses when it lifts within the touch slop of where it went down (`computeHitSlop` with the window's gesture settings, so the zoom doesn't matter); a drag or scroll keeps the keyboard. A mouse, a stylus or an unknown pointer, and any pointer on desktop, unfocuses on the way down, Flutter's own default. The field's tap-region group counts as inside: other fields, its paste and clear buttons, selection handles and toolbar, and the iOS bar. A button elsewhere still fires; the field unfocuses first.
- **The iOS bar** (`KeyboardAccessoryHost`, inside the zoom): over the pads `hasNoReturnKey` names (a number keyboard without `signed`, and phone), on a field that isn't read-only, while the keyboard is up. **Next** (only when the field's `textInputAction` is next; what the return key would do) and **Done** (unfocus), text buttons on `surfaceContainerHigh` whose labels shrink rather than wrap, no tooltips (nothing above the Router has an Overlay). Its height (`keyboardAccessoryBarHeight`) is added to the subtree's `viewInsets.bottom`, so Scaffolds shrink above it, the focused field scrolls clear of it, and dialogs and sheets lift over it. It is in a `TextFieldTapRegion` and `ExcludeFocus`, so tapping it is "inside" and takes no focus. After Done it stays, buttons off, until the keyboard is down, so it slides away with it. Off iOS, and on the web (Safari has its own bar), it returns its child and listens to nothing. The tree shape never changes, so it never remounts the Router.
- **Not done:** `keyboardDismissBehavior.onDrag`, which would close the keypad on every form scroll.

### Status bar

The status bar's icons must read on the app's theme whatever the phone's light / dark mode. iOS reads only `statusBarBrightness` (which nothing used to set, so it followed the phone's mode), Android `statusBarIconBrightness`, and no AppBar reaches the status bar under the shell's SafeArea, so an `AppBarTheme.systemOverlayStyle` never applies (the theme sets none). The styles live in `system_ui_style.dart`, each setting both platforms' fields:

- **App:** `AppFrame`'s `_SystemUiStyleScope` puts `AnnotatedRegion(appSystemUiStyle(Theme.brightnessOf(context)))` over the window: a transparent bar with `statusBarIconBrightness` (Android) and `statusBarBrightness` (iOS, the brightness of what's behind the bar) for the resolved theme, so switching Light / Dark / System flips it. It sits outside the zoom, so keyboard frames don't rebuild it. MaterialApp also sends a style whenever it builds its theme; a region is read at the end of every frame, so the region's wins.
- **Navigation bar fields stay null,** so Android's navigation bar looks exactly as before. Never use `SystemUiOverlayStyle.light` / `.dark`: they force a black navigation bar.
- **Splash:** its own region with `kSplashSystemUiStyle` (light icons over the teal) wins while it's drawn (see Splash Screen).
- **First frame:** `main()` sets `initialSystemUiStyle(splash:, themeMode: Settings.primedThemeMode, platform:)` before `runApp`, so the native launch screen hands over to a readable bar.

### Camera access

mobile_scanner shows a camera that won't run as a black box with its own English text, and iOS never asks twice: after Don't Allow only the system's Settings can allow the camera. So the app says why in its own language and offers the way out (`scanner_camera.dart`, `device_channel.dart`), for both scanners and the product photo:

- **`CameraSession`** (one per scanner screen): starts the camera while the screen is shown (`setVisible(TickerMode…)`) and the app is resumed, stops it otherwise, one operation at a time. A refused camera is asked for again only when the screen opens or on **Allow camera** / **Try again** (`retry`), never on resume (Android's prompt pauses and resumes the app, which would loop). On resume it re-reads the permission (`DeviceChannel.cameraAccess()`), so back from Settings with the camera allowed it starts by itself. It keeps the last start's error, since mobile_scanner clears its own on any later state change (an iPad turning) while the camera is still off.
- **`ScannerErrorView`** (in `ScannerPreview`, instead of the frame and hint), white on black, scrolling, translated:

  | State | Says | Buttons |
  | --- | --- | --- |
  | refused, may ask again (Android after a first Deny; iOS not yet asked) | Camera access is off + `cameraAllowPrompt` | Allow camera, Open Settings |
  | refused for good (iOS after Don't Allow, Android "don't ask again") or unknown | Camera access is off + `cameraAllowInSettings` | Open Settings |
  | restricted (Screen Time, a profile) | Camera access is off + `cameraRestricted` | — |
  | no camera | `noCameraAvailable` | — |
  | failed to start (or allowed meanwhile) | `cameraStartFailed` | Try again |

  Until the permission check answers after a refusal it shows only the icon and title, so no wrong message flashes. **Open Settings** opens the app's own page in the system's Settings (`openAppSettings`).
- **`TorchButton`** (the app bar's flashlight): drawn from the controller's `torchState`, hidden unless the camera runs and has a flashlight (iPads and some Android phones have none); the toggle is awaited and its errors caught.
- **Product photo:** the picker's `camera_access_denied` / `camera_access_restricted` open `showCameraBlockedDialog` (Open Settings, or only Close when restricted) when the access is permanentlyDenied, restricted or unknown. A first Deny on Android, which may ask again, stays silent; on iOS the dialog follows the first Don't Allow. `no_available_camera` and other failures show a snackbar.
- **Android can't tell** "never asked" from "don't ask again": both read as `permanentlyDenied` (`shouldShowRequestPermissionRationale` is false), so the status is read after a refusal, never before the first ask.

### Barcode lookup

iOS (Apple Vision) reports a 12-digit UPC-A as the 13-digit EAN-13 with a leading 0; Android (ML Kit) reports the 12 digits. `barcodeLookupForms` asks for both spellings, so a code saved from either phone's scan is found by the other's.

- **`ProductRepository.findByScannedCode(raw)`**: active products only (the Recycle Bin's soft-deleted ones no longer match), whose `qrCode`, `sku` or a variant combination's `sku` equals any form, case-insensitively, the code trimmed. A variant SKU opens its product. The Scanner tab uses it; "Add as new product" pre-fills the trimmed code, and the product form's QR scanner returns it trimmed (a blank code doesn't close it).
- An EAN-13 that doesn't start with 0, EAN-8, QR text and SKUs are looked up only as scanned.

### Tablets and iPad

Phones stay in portrait; tablets (iPad, Android tablets) rotate and multitask, on both platforms.

- **Orientation** (`OrientationPolicy`): from the display's shortest side, not the window's (Split View and Android's split screen narrow the window): ≥ 600 dp (`kTabletShortestSide`) allows every orientation (an empty list, the system's default, which on an iPad also allows Split View and Slide Over), below that portrait up and down, and portrait while the size is unknown. `didChangeMetrics` re-applies it only when the decision changes (a foldable folded or unfolded). Info.plist keeps iPhone portrait-only and the iPad's four orientations with no `UIRequiresFullScreen`; the Android manifest sets none.
- **Share sheets point at the control tapped.** On an iPad (and a Mac) the share sheet is a popover anchored to a rect; without one it opens from the middle of the screen. `shareOriginOf(context)` gives the control's rect in window coordinates, the Display size zoom included, for `ShareParams(sharePositionOrigin:)`; the app's share helpers (`sendDueReminder`, `shareCustomerStatement`, the `CsvExportService` exports, `exportBackup`, `savePdfWithSystemSheet`) take it as `shareOrigin`. Call sites read it from a `Builder` around the control, or from a `GlobalKey` when the rect is read later (the catalog's buttons, the Reports export slot, the order detail's menu button, Settings' Export Backup row). Printing (`layoutPdf`) and the file pickers present as form sheets on an iPad and take no anchor (from their plugins; not yet tried on a device).
- **Calls** (`callPhone`): `launchUrl(tel:)` answers false on iOS and throws on Android where the device can't call (most iPads, an iPod touch, a tablet without a dialer); then a sheet shows the number (selectable, left to right in every language) with **Copy number**. Also when the phone has no digits, and for iOS `tel:` links with `*` or `#` (USSD), which iOS refuses. Used by the Due Book, supplier detail and order detail call buttons. No `<queries>` / `LSApplicationQueriesSchemes` entry is needed: nothing calls `canLaunchUrl`.
- **Flashlight:** hidden on devices without one (`TorchButton`, see Camera access).
- **Layout:** the sidebar gets labels from a 600 dp window (`kSidebarExpandMinWidth`), and the order card picks its row layout from its own width (`OrderCard.rowLayoutMinWidth`). Tablet and Split View layouts are tested (`forEachTabletLayout`, see the layout harness).
- **Guard:** `test/platform_parity_guard_test.dart` fails on a `SharePlus` share (or `Printing.sharePdf`) without its anchor, a share-helper call without `shareOrigin`, or a `tel:` link outside `call_phone.dart`.

### Sub-pages and iOS swipe back

- **Page type:** every sub-route (23) is built by `_subPage`. On iOS it's a `MaterialPage`: the theme sets no `pageTransitionsTheme`, so iOS gets `CupertinoPageTransitionsBuilder`'s slide and the native back swipe from a 20 dp strip at the page's own leading edge, which in the shell starts beside the sidebar. On Android and the web (where Safari's own edge swipe goes back in the browser) it's `_fadePage`, go_router's `CustomTransitionPage`, which has no swipe. The screens pushed with `Navigator.push(MaterialPageRoute)` (the color theme editor, the product form's QR scanner, the order detail's Create Return) swipe the same way.
- **From the screen edge over the sidebar** (`ShellEdgeBackSwipe`, `shell_back_swipe.dart`), on iOS when the sidebar is on the leading side (`!isRight`; the Row's first child, so the right edge in Arabic and Urdu): a strip at the physical screen edge, outside the shell's SafeArea, `max(edge inset, 20 dp)` wide (`PositionedDirectional`). A translucent `Listener` feeds a `HorizontalDragGestureRecognizer`, so the sidebar keeps its taps, long presses and scrolls. The recognizer joins a touch only when the current branch's top route (from its `BranchTopRouteObserver`) is a Material or Cupertino page that is current, done animating, `popGestureEnabled` (not a tab's first screen, not `PopScope(canPop: false)`) and on that navigator, with no gesture under way; and it takes the touch only past the slop (`onlyAcceptDragOnThreshold`, else a tap or resting thumb on empty rail space would start a swipe).
- **The drag** uses the route's public back-gesture API (`PredictiveBackRoute`): `handleStartBackGesture`, then `handleUpdateBackGestureProgress` with the local delta ÷ the navigator's width (read once at drag start; local units, so the page follows the finger 1:1 at any Display size). On release, Flutter's own rule: a fling of ≥ 1 width/s decides by direction, else past halfway pops. Keep → `handleCancelBackGesture()`; pop → `navigator.pop()`, which slides from where the finger left the page (`handleCommitBackGesture` would start from all the way in, a visible jump); then `didStopUserGesture()` exactly once when the animation ends, also if the page is removed mid-slide (a gesture left running keeps the tab ignoring touches). The rest of the shell ignores touches while a page follows the finger.
- **Edge cases:** a branch switch, the strip being disabled, or the shell's disposal mid-swipe abandons it after the frame (the page put straight back, since an offstage branch's animation is frozen by `TickerMode`). A page the app covers mid-swipe (the order form's "Order created" sheet) slides back in, as Flutter's own iOS swipe would, through the route's own (protected) controller: the back-gesture API moves only a page on top. After release the page finishes linearly over its remaining share of the transition, where Flutter's own swipe eases it

## State Management Pattern

- **Stream providers** for reactive lists (products, customers, suppliers, …), built on `reloadOn(collection.watchLazy(), load)`, not `watch(fireImmediately: true)` (see Performance). Big lists load on a worker via `runDbJob`. Long histories are paged notifiers (`OrderPages`, `StockMovementPages`, `CustomerOrders`)
- **One-row providers** (`orderById`, `productById`, `customerById`, `supplierById`): yield `getSync(id)`, then `watchObject(id)` without `fireImmediately`. Detail screens read these instead of creating streams or futures in `build()`, because go_router rebuilds pages on every push/pop in the branch, and each rebuild resubscribed, flashed a spinner and re-queried
- **Revision counters** (`isar_revisions.dart`) for providers that run their own queries (dashboard stats, reports), so nothing deserializes a whole collection just to notice a write
- **Notifier classes** for mutations (add, update, delete, complex transactions). Per-item reads and writes inside a `writeTxn` are batched (`getAll` / `putAll`)
- **AsyncValue.guard()** for error handling
- **Isar `watch` / `watchObject(fireImmediately: true)`** remains only for small or one-off streams: categories, the trash bin, `lowStockProducts`, `pendingOrders`, the order/purchase product pickers (created once in `initState`), purchase detail and stock adjustment (one row each), and the repositories
- **StreamBuilder** for real-time stock in product picker and stock adjustment screens
- **Freezed** for immutable dashboard stats (DailySales, DashboardStats)
- **DashboardDateRange notifier** for date filter state (Today/This Week/This Month/Custom)
- **Settings provider** (keepAlive, SharedPreferences): shopName, currencySymbol (default `$`), lowStockThreshold, themeMode, taxRate, language, lastBackupTime, colorThemeId, customColorThemes and more. Watch single keys with `ref.watch(settingsProvider.select(...))`, selecting plain values (the custom themes are kept as JSON text for this); watching the whole map rebuilds on every settings write
- **Device and service providers** (keepAlive) that screens read instead of constructing, so tests swap them: `deviceChannelProvider` (`FakeDeviceChannel`), `imagePickerProvider`, `authGateServiceProvider`, `updateChannelProvider` (`UpdateChannel.none` keeps a test off GitHub). A test of the scanners also sets `MobileScannerPlatform.instance = FakeCamera(...)` (`test/support/fake_camera.dart`)

## Performance (large datasets)

The app is tuned against a generated dataset of about 10 000 orders (`tool/perf_dataset.dart`), because most slowdowns grow with orders, payments and movements. Isar deserializes query results on the isolate that runs the query, so a big load freezes that isolate, together with the Dart work done on the results.

- **Worker jobs — `runDbJob(isar, job)`** (`db_worker.dart`): runs a *synchronous* job (`findAllSync`, `txnSync`, `writeTxnSync`, …) through `compute`, which is `Isolate.run` on native. The worker opens the same DB with `kIsarSchemas`. Isar shares the native instance between isolates, and the worker's `close()` releases only its own reference. The result comes back via `Isolate.exit`, uncopied. On web the job runs inline. **Jobs must be built by top-level functions from plain values** (`salesReportJob(start, end)`, `restoreBackupJob(bytes)`, …) and never capture a `Ref`, a `BuildContext` or the caller's `Isar`: a closure carries its whole context across isolates, and those can't cross. Current jobs: Due Book (`loadDuesSync`), dashboard (`dashboardStatsJob`), the four report jobs, the products / orders / movements lists and pages, customer history (`customerOrdersJob`), CSV orders export, backup encode (`backupBytesJob`), restore (`restoreBackupJob`), Clear All Data (`clearAllDataJob`), balance recalculation (`recalculateOutstandingBalancesJob`).
- **Live lists — `reloadOn(changes, load)`** (`isar_reload.dart`): Isar's `watch()` is `watchLazy().asyncMap(findAll)`, one full query per change event with none skipped. Riverpod 3 pauses providers whose widgets are offstage, and go_router keeps visited branches mounted under `TickerMode(false)`. A hidden tab therefore queued events and replayed one full reload each when shown, and a transaction touching two watched collections reloaded twice. `reloadOn` only marks the data dirty: it subscribes *before* the first load, coalesces bursts within 16 ms, runs one load at a time (a change during a load costs one more load after it), never loads while paused, and loads once on resume if anything changed. `mergeChanges([...])` combines several `watchLazy()` streams; paged notifiers also merge their own "load more" stream.
- **Revision counters** (`ordersRevisionProvider`, `customersRevisionProvider`, `productsRevisionProvider`, `expensesRevisionProvider`, `paymentsRevisionProvider`): keepAlive ints bumped by `watchLazy()`. They are never paused, so writes made while the Dashboard or Reports is offstage collapse into one recompute when it's shown. `dashboardStats` and the sales / dues / inventory reports watch them instead of full list providers. Nothing watches `paymentsRevisionProvider` yet.
- **Indexes:** see Data Models → Indexes, including the id-order pitfall.
- **Paging:** 100 rows per page. A list asks for the next 100 when it builds a row within 20 of the end (scheduled after the frame, since the notifier can't change during a build), and shows a spinner row while more exist. Each page query fetches `limit + 1` rows to know whether more exist. Tab badges are native `count()`s. Paged: the Orders tabs (`order_pages_provider.dart`), inventory movement history, and customer purchase history. Exports never depend on how far a list was scrolled.
- **Batched writes:** see `_moveStock` (Order Status Change), `_productsById` (Purchase Recording), `collectFromCustomer`, `processRecurringOrders` (one transaction for all due copies). Each batch applies items in order to an in-memory map, so results match the old sequential get → put exactly. `test/batched_writes_test.dart` pins them.
- **PDF pipeline:** capture (`captureWidgetPng`, which unmounts the off-screen tree afterwards) → `assemblePdf` on a background isolate, with full-page outputs (report, statement, catalog PDF) re-encoded to JPEG q75. The invoice stays PNG. Bitmaps on a page (catalog photos, placeholder, watermark icon) are pre-decoded at draw size and drawn with `RawImage`, so a capture never waits on an async image load. `runWithProgress` puts up the spinner before the work starts.
- **Startup:** `.env` and SharedPreferences load in parallel (`.env` must still be loaded before `runApp`, because DriveService reads it). When Phone colors is the saved color theme, `main()` also waits for the system palette before `runApp` (500 ms timeout); every other primed value is read synchronously. The splash shows only on first launch. Notification init runs off the critical path except on iOS. Icon warm-up and Workmanager registration (`keep`, Android only) happen after the first frame, and the auto-backup catch-up 15 s later (not on iOS). Isar `compactOnLaunch` keeps the file compact after big restores or clears.
- **UI:**
  - `AnimatedEntrance` animates only a list's first screenful. It decides once, on mount, and shows the child immediately if its `Scrollable` is already scrolled or its index is past `3 × maxStaggerIndex`, so a fling never reveals blank rows still waiting to animate.
  - Both scanners (the Scanner tab and the product form's QR scanner) run `MobileScannerController(autoStart: false)` through a `CameraSession` (`scanner_camera.dart`), which starts/stops the camera from `TickerMode` (branch offstage or covered) + app lifecycle. Calls are serialized through one future chain, because `start()` throws while a start is in flight. A refused camera is asked for again only when the screen opens or on Allow camera / Try again: Android re-prompts on every `start()`, and the prompt pauses/resumes the app, which loops. On resume it only re-reads the permission, so a camera allowed in Settings meanwhile starts by itself (see Camera access).
  - fl_chart compares chart data, callbacks included, with `==`, so an inline closure restarted the animation on every parent rebuild. Chart callbacks are State-method tear-offs or statics (`GridLineCallback` hands out one per color, so a theme switch still repaints), and charts sit in `RepaintBoundary`s.
  - Products grid: `_ProductGridDelegate` picks the column count at layout time (`(width + 32) / 180`, clamp 2–6), so a keyboard-driven height change relays out without rebuilding cards.
  - Images are decoded at display size: product card `cacheWidth`, catalog avatar `ResizeImage`, splash logo `cacheWidth`.
  - Product form: typing in an attribute or option only schedules regeneration (300 ms debounce, flushed on submit). Regeneration keeps entries and controllers by combination key, so typed stock / price / SKU survive. Combination rows are built lazily, but every `FormField` stays in the always-mounted first `SliverToBoxAdapter`: a lazily built `FormField` scrolled out of the cache extent is unmounted, and `Form.validate()` silently skips it.
  - Long detail pages (cash register, customer, supplier) are slivers with `SliverList.builder`, so history only builds what's on screen.

  - Dashboard: stat cards via `Wrap` + `LayoutBuilder` (2-6 cols based on `width/170`, height `statCardHeight`); charts side-by-side on wide screens; date-range filter bar
  - Product grid: responsive columns from `_ProductGridDelegate` at layout time (body `width/180`, clamp 2-6)
  - Order card: compact column, or a single row when the card itself is at least 512 dp wide (`OrderCard.rowLayoutMinWidth`)

- **Dashboard charts**: Weekly sales bar chart, order status pie chart, revenue vs expenses line chart
- **Dashboard SliverAppBar**: `title:` ("Micro Seller") always shown; `expandedHeight: dashboardHeaderHeight(textScaler)` — 160 at the default text size, growing by exactly what its three text lines (date pill, revenue label, amount) grow, so a larger font never clips the stats; `flexibleSpace` holds greeting + date pill + today's revenue/total-orders stats with top padding `kToolbarHeight + 8` so content sits below the toolbar layer. Title remains visible when collapsed. The header is the theme's `context.brand.gradient` with `brand.onPrimary` text (white and white70 on Teal); the Reports header does the same.
- **Reports screen**: four tabs over one date range — **Profit & Sales** (P&L statement, net sales chart by day or month, sales by payment method, orders by status, top products / categories / customers), **Dues & Payments** (money received by method, dues collected, credit given, refunds; receivable + aging *as of today*; top debtors), **Stock & Returns** (stock value at cost / selling price, potential profit, movements by type, best sellers, not-sold-in-period, return reasons), **Purchases & Expenses** (purchased / paid / unpaid, owed to suppliers today, top suppliers, expenses by category, cash register cash in/out and over/short). Export shares the current tab as PDF (Unicode-safe) or CSV (UTF-8 BOM for Excel).
- **Report accounting rules**: returns count when their goods are back (`returnStatus` received/refunded), dated `updatedAt ?? createdAt`, and are *subtracted* (the old single-page report added them to revenue). Gross sales are goods at list price; order discounts are their own row; returns are valued at `netGoods` (after their discount share, without tax). Tax is shown as "Tax collected", never sales; delivery is added after gross profit. Sales by payment method, top customers and average order value stay on billed `totalAmount`. Net margin is 0 when net sales ≤ 0 (a ratio over a negative base flips sign). COGS uses `OrderItem.costPrice`, falling back to the product's current cost when 0, and returned items reverse their COGS. Stock value, receivable and supplier dues are point-in-time ("as of today"). Returns against a cancelled original are ignored (the cancel already removed the sale). Pending orders count as sales (same as the Due Book). "Owed to suppliers" = Σ `Supplier.totalDue` + unlinked purchases' `balanceDue` (direct supplier payments don't touch purchases). Cancel reversals (`Payment.note == kCancelledPaymentNote`) net out of money received; "Refunds paid" is return refunds only. Known trade-offs: a return is dated `updatedAt`, so refunding it later moves it to the refund date; legacy zero-cost items use today's product cost. `ReportTable` cells are String/int/double — money stays numeric in CSV (formula-like text is apostrophe-escaped), and `formatCell` formats it for the PDF.
- **Reports header** (was SliverAppBar-only): `NestedScrollView` + pinned `SliverAppBar` (range chips + date line in `flexibleSpace`, scrollable `TabBar` in `bottom`). `expandedHeight` is `reportsHeaderHeight(textScaler, tabBar.preferredSize.height)`: toolbar + chip row (`reportsChipRowHeight`, 36 at the default text size) + date line + the TabBar's own height, so both text rows grow with the text size without clipping or sliding under the tabs. The date line stays one line and shrinks (`FittedBox`) rather than wrapping. Previously: `title:` ("Reports") always shown; `expandedHeight: 120`; `flexibleSpace` holds the start/end date chips with same `kToolbarHeight + 8` top padding pattern.
- **Customer detail chart**: 6-month purchase history bar chart
- **FABs**: Icon-only `+` with tooltip, rounded-square shape (16px radius)
- Cards with 14px radius, subtle shadows
- Color-coded text-only status badges (no icons in badges)
- Shimmer loading, empty states, confirm dialogs

### Toolchain

- **CI builds with the Flutter pinned in `.github/actions/setup-flutter/action.yml`** (`flutter-version` + `channel`). `./release.sh` sets it to the Flutter of the Mac that releases (`flutter --version --machine`, looked up in Flutter's `releases_linux.json` for the channel) and makes `pubspec.lock` with that Flutter. ### CI/CD (GitHub Actions)

README → For developers → Releases is the short version for contributors; the details are here.

- **One-time setup** (GitHub settings, not files): the `release` environment holds the secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` and `DOTENV` (the whole real `.env`; it must give `GOOGLE_OAUTH_WEB_CLIENT_ID`, and it ships as plain text inside the app), plus `ANDROID_SIGNING_CERT_SHA256` (a variable, or a secret). `bash tool/ci/copy_release_secrets.sh`, run on the Mac with the keystore, puts each value on the clipboard in turn and prints the SHA-1 the Android OAuth client needs. The iOS build needs no Apple account and no other secret.
- **`./release.sh`** (repo root) cuts a release in one command:
  - Syncs `main` with GitHub: stash, fast-forward, unstash. A conflict only in `pubspec.lock` keeps the local copy, because the lock is re-made anyway.
  - Pins CI to this Mac's Flutter.
  - Picks the version: pubspec's if it isn't tagged yet, else the next patch. The build number is higher than every one ever committed or tagged.
  - Asks once, then runs the `ci.yml` checks locally.
  - Commits everything as `chore: release vX.Y.Z+N` and pushes `main` and the annotated tag in one `--atomic` push. A failed push undoes the commit and the tag.
  - Follows the run through GitHub's public API, polling every 60 s (unauthenticated calls are limited to 60 an hour; 20 s with a token), then opens the draft.
  - It runs on macOS's bash 3.2. The owner runs it; Claude never does, because it commits and pushes.
- `.github/actions/setup-flutter` is the one place the CI Flutter version is pinned (see Toolchain). It runs `flutter pub get --enforce-lockfile`, and when that fails it explains that the lock doesn't fit the pinned Flutter.
- `ci.yml` (PRs, pushes to `main`, and called by `release.yml`): generated code must be committed and current, l10n parity, `flutter analyze --no-fatal-infos` (errors and warnings fail), `flutter test` — and **no skipped tests**, since the real-Isar tests skip themselves when the Isar core library isn't found. Its `ios` job builds the app unsigned on `macos-26` beside the checks (`flutter build ios --release --no-codesign`): `pubspec.lock` must not change, and a change under `ios/` (Flutter migrating the Xcode project during the build) is a warning to commit it. `release.yml` calls it with `skip-ios: true`, because its own `ios` job builds the real app and the Android release mustn't wait for a macOS runner.
- `release.yml` (tag `vX.Y.Z` = `v` + pubspec version name, or a manual run on `main`):
  - `android`: signed AAB + universal and split APKs in the `release` environment (required reviewer; signing secrets live only there), checked by `tool/ci/verify_android_artifacts.sh`.
  - `ios`, beside it on `macos-26` (the `release` environment only for `DOTENV`): `flutter build ios --release --no-codesign --obfuscate --split-debug-info`, with any `-rc` suffix dropped from the version (Apple wants three numbers, and Flutter would turn `1.0.5-rc.1` into `1.0.5.1`; the build number still tells them apart). It zips `Payload/Runner.app` into `micro-seller-vX.Y.Z-unsigned.ipa` and checks it with `tool/ci/verify_ios_artifacts.sh`: one `Payload/<name>.app`, the bundle ID, version and build number, an arm64 `iphoneos` release build with Flutter, the Dart code and the `.env` asset, `GIDClientID` with its URL scheme, and the camera / photo library / Face ID texts.
  - `publish` makes a **draft** GitHub Release that is published by hand. It waits for `ios` but needs only `android`: the APKs are drafted whatever happens to the `.ipa`, which joins (with its `SHA256SUMS.txt` line and the iPhone notes) only when the iOS build passed and the file matches its checksum. Re-running refreshes a draft, adding or removing the `.ipa` and its notes; when the iOS build passed but its `.ipa` didn't reach the draft, the job fails after drafting the Android files (re-run the iOS job). The publish job uploads again, then fails, if any file isn't fully attached to the draft.
  - The AAB (`play-bundle`) and the obfuscation symbols (`symbols`; `ios-symbols`: Dart symbols + dSYMs) are run artifacts (they expire: archive them). The `.ipa` is also one (`ios-ipa`), but the release keeps its copy.
- `REQUIRE_RELEASE_SIGNING=true` makes `android/app/build.gradle.kts` fail instead of falling back to the debug key when `key.properties` is missing.
- **Never committed** (`.gitignore`): `.env`, Android signing (`android/key.properties`, `*.jks`, `*.keystore`) and Apple signing (`*.p12`, `*.p8`, `*.mobileprovision`, `*.cer`), for when App Store signing comes. Also ignored: `android/.kotlin/` (the Kotlin Gradle cache).
- Actions are pinned to commit SHAs; Dependabot (`.github/dependabot.yml`) keeps them current.

### Build Commands

```bash
# Debug
flutter run

# Release APK (for testing)
flutter build apk --release

# Release AAB (for Play Store upload) — preferred form
flutter build appbundle --release --obfuscate \
  --split-debug-info=build/debug-info --tree-shake-icons
# Output: build/app/outputs/bundle/release/app-release.aab

# Verify signer, version and 16 KB alignment (every LOAD segment, arm64 + x86_64)
# of APKs/AABs — the same checks as CI's release job:
#   NDK_VERSION=28.2.13676358 tool/ci/verify_android_artifacts.sh <cert-sha256> <name> <code> <files>
# Quick manual look at the first LOAD segment of the arm64 libs:
LREAD=$ANDROID_HOME/ndk/28.2.13676358/toolchains/llvm/prebuilt/darwin-x86_64/bin/llvm-readelf
cd build/app/intermediates/merged_native_libs/release/mergeReleaseNativeLibs/out/lib/arm64-v8a
for f in *.so; do
  align=$("$LREAD" -lW "$f" | awk '/^  LOAD/ {print $NF; exit}')
  printf "%-35s %s\n" "$f" "$align"   # want 0x4000 or 0x10000 for every row
done

# Unsigned iPhone app, as CI builds it (an .ipa is a zip of Payload/Runner.app)
flutter build ios --release --no-codesign
# Check an .ipa (macOS) with the same checks as CI's release job:
#   bash tool/ci/verify_ios_artifacts.sh com.blackshadowsoftware.microseller <x.y.z> <build> <file.ipa>

# Generate launcher icons (after placing icon in assets/icons/app_icon.png)
dart run flutter_launcher_icons
```

Play Store uploads are manual: upload a tag run's `play-bundle` artifact (the AAB signed with the upload key), or an AAB built as above, in Play Console.

## Platform Support

Android, iOS (min 16.0), Web, macOS (min 13.0), Linux, Windows. Android ships on Google Play and as signed APKs on GitHub Releases; iOS as an unsigned `.ipa` on GitHub Releases, sideloaded (see Build & Release → iOS Config). Installs that no store updates (the iPhone app, GitHub APKs) get the update notice (see Key Business Flows → Update notice). Phones run in portrait; tablets (iPad, Android tablets) rotate and multitask (see Tablets and iPad). Web has no worker isolates or native Isar core, so `runDbJob` runs jobs inline there.
